CSS organization: BEM-lite

Day 35 · Week 6 Naming, file split and comments.

The big idea. A messy room works fine until you need to find something. One huge CSS file is the same. Organizing your CSS means three habits: clear names, the right files, and helpful comments. Then you, or a teammate, can find any rule in seconds.

Classwork task: refactor your project CSS. Split the styles into files, use consistent names, and leave no abandoned rules.

Homework: do the same refactor on your resume.

Mission: measure the mess first

Open your project CSS and count three things: how many class names look different from each other, how many rules no HTML uses, and how many comments explain why. Write the numbers down, then count again after your refactor.

refactor

Make the code tidier without changing how the page looks. Same page, better code.

Naming

BEM-lite: .block, .block__element, .block--modifier. Name things by what they are.

File split

base.css for the basics, layout.css for page structure, components.css for reusable pieces.

Comments

Short section headings, and notes that say why, not what.

Abandoned rule

CSS that nothing uses any more. Delete it. Git remembers it if you ever need it back.

Naming: BEM-lite

BEM stands for Block, Element, Modifier. “Lite” means we keep only the easy parts. Pick a block name and a modifier and watch the class names and the code change.

.card

Block. A part that can stand on its own.

.card__title

Element. A part that lives inside a block. Join it with two underscores.

.card--featured

Modifier. A variation of the block. Join it with two hyphens, and always use it together with the block class.

BEM-lite rules: lowercase letters, hyphens inside words (.site-header), name by purpose and not by looks, only one level of element, style with classes (not ids), and a modifier never stands alone.

    


    

        
How to choose names: block, element or modifier?

        
Look at one piece of your page and ask three questions:

        
    
            
  1. Could this piece live somewhere else on the page, or on another page, and still make sense? If yes, it is a block. Examples: .card, .btn, .site-header, .nav.
    2. 
            
  2. Does it only make sense inside one block? If yes, it is an element of that block: .card__title, .nav__link. A card title with no card is just a heading.
    3. 
            
  3. Does the block come in a different version? A bigger one, a highlighted one, a dark one? Each version is a modifier: .card--featured, .btn--large.
    4. 
        

        
Block names are nouns (what it is). Modifier names are adjectives (how this version is different). Use the same words everywhere, so a teammate can guess a class name before reading the CSS.

        

            
Example: a navigation bar


.nav                 block
.nav__list           element
.nav__item           element
.nav__link           element
.nav__link--active   modifier of the link

            
The same names in HTML


<nav class="nav">
  <ul class="nav__list">
    <li class="nav__item">
      <a class="nav__link nav__link--active"
         href="index.html">Home</a>
    </li>
  </ul>
</nav>

        

        
Why “lite”? Full BEM has extra rules: deeper nesting, prefixes like c- and l-, and “mixes”. BEM-lite drops all of that. You keep block, element and modifier, with only one level of element. That is enough for a school project.

    


    

        
Why flat class names win: a little about specificity

        
When two rules try to style the same element, the browser must pick one. It uses specificity, which is a score for how strong a selector is. It counts three things, strongest first:

        

            

                
StrengthWhat countsExamplesScore (ids, classes, tags)

                
                    
Strongestids#header1,0,0

                    
Middleclasses, attributes, pseudo-classes.card, [type=text], :hover0,1,0

                    
Weakesttag namesh3, p, a0,0,1

                
            

        

        
The browser compares scores from left to right. An id beats any number of classes, and a class beats any number of tags. If two scores are equal, the rule written later wins.

        

            

                
SelectorScoreComment

                
                    
.card__title0,1,0One class. Easy to override when you need to.

                    
.card h30,1,1Looks small but is stronger than a single class.

                    
.box1 .big-button:hover0,3,0Two classes plus :hover. Hard to beat later.

                    
#header1,0,0Beats any number of classes.

                
            

        

        
The BEM-lite trick: every selector is one class, so every rule scores 0,1,0. Then only the order of your rules decides, and you control the order. No surprises, and no need for !important.

File split: three files, three jobs

        

            

                
FileIts jobWhat goes inside

                
                    
base.cssThe foundations. Applies to the whole site.Variables in :root, the box-sizing reset, body font and colours, headings, links and images (plain tags).

                    
layout.cssThe skeleton. Where the big parts sit.The page grid, containers, header, main and footer placement, spacing between sections, and media queries that move or stack big parts.

                    
components.cssReusable pieces.Cards, buttons, nav links, badges, forms: anything with a BEM-lite block name.

                
            

        

        

            
Folder layout


project/
├── index.html
└── css/
    ├── base.css
    ├── layout.css
    └── components.css

            
Link them in this order


<link rel="stylesheet" href="css/base.css">
<link rel="stylesheet" href="css/layout.css">
<link rel="stylesheet" href="css/components.css">

        

        
Order matters. A later file can override an earlier one, so put foundations first, then layout, then components.

    


    

        
Which file? Ask three questions

        
    
            
  1. Is it a variable, a reset, or a style for a plain tag that applies to the whole site? Put it in base.css.
    2. 
            
  2. Does it decide where the big parts of the page sit, how wide they are, or how they stack on small screens? Put it in layout.css.
    3. 
            
  3. Is it a named, reusable piece with its own look (card, button, nav, form)? Put it in components.css, together with its elements, its modifiers and its own small-screen tweaks.
    4. 
        

        
Not sure? Ask: “If I copy this piece to another page, which rules must come with it?” Those rules belong in components.css.

        
Link or @import?

        
Use one <link> tag per file in the <head>, in the order base, layout, components. You can also write @import inside CSS, but then the browser must download the first file before it even finds the next one, which is slower. Stick with <link>.

        
Keeping each file tidy

        
    
            
  • Keep a steady order inside a file: variables first, then plain tags, then classes.
    • 
            
  • Put a component’s own small-screen tweak next to that component, not in a faraway file.
    • 
            
  • One component per section, each with a banner comment.
    • 
            
  • When a file grows very long, split components into more files later (for example card.css and button.css). Three files are enough for now.
    •

Comments: say why, not what

        

            
Helpful


/* ===== Components: card ===== */

.card {
  padding: 16px;
  border-radius: 12px;
}

/* Featured cards get a thick border so they stand out in the grid. */
.card--featured {
  border-width: 4px;
}

            
Not helpful


/* set padding to 16px */
.card {
  padding: 16px;
}

/* .old-card { color: red; } */
/* TODO fix this??? */
.box1 { margin: 0; }

        

        
    
            
  • Start each section with a short heading comment, like /* ===== Layout: header ===== */.
    • 
            
  • Explain why a rule exists. The code already shows what it does.
    • 
            
  • Do not leave old code commented out. Delete it. Git remembers.
    • 
            
  • If you must leave a note for later, make it specific: /* TODO: stack cards under 600px */.
    • 
        

        
Comment syntax: CSS only understands /* ... */. A comment can run over many lines. A JavaScript-style // comment does not work in CSS, and it can break the rule that comes right after it.

        
Good reasons to comment: the start of a section, a “magic number” (why exactly 56px?), a workaround for a browser problem, and a decision that is easy to break (such as “this rule must stay after .card”).

    


    

        
No abandoned rules

        
An abandoned rule is CSS that nothing uses any more. It makes you read more, and it can surprise you later by styling the wrong thing. Here is how to find them:

        
    
            
  1. Take each class name in your CSS and search for it in your HTML. In VS Code, press Ctrl + Shift + F (Windows) or Cmd + Shift + F (Mac) to search every file.
    2. 
            
  2. No match? The rule is probably abandoned. Delete it. Git keeps the old version.
    3. 
            
  3. Be careful with rules that look unused. They might style something that only appears on another page, on hover, or on a small screen.
    4. 
            
  4. Chrome DevTools can help. Open Coverage from the “More tools” menu, reload the page, and unused CSS is marked in red. It only knows about the page you loaded.
    5. 
            
  5. Look at the page before and after. It must look exactly the same. That is what makes it a refactor.
    6. 
        

    


    

        
Worked example: refactor a messy project, step by step

        
We refactor the messy file from the start of this lesson. At the end the page must look the same. Follow the steps, then use the buttons to read every file.

        
    
            
  1. Save a snapshot. Commit your work with git commit and take a screenshot. This is your “before”.
    2. 
            
  2. Make the three files inside a css/ folder, and link them in order in the HTML.
    3. 
            
  3. Move each rule into the right file using the three questions.
    4. 
            
  4. Rename classes. Change the HTML and the CSS together, so nothing breaks. Use find and replace in your editor.
    5. 
            
  5. Delete rules that no HTML uses, and delete commented-out code.
    6. 
            
  6. Add comments: a banner for each section, and a note wherever the reason is not obvious.
    7. 
            
  7. Compare the page with your screenshot, and fix any difference.
    8. 
            
  8. Commit with a clear message, such as refactor: split css into base, layout and components.
    9.

Ship check
Day 36 · On-spot Eval 6 · Week 6 Grid project + Pages.

    


    

        

            
The big idea. “Shipping” means your project works for someone else, on the internet, and not only on your own laptop. Today your faculty opens your live URL and browses your Grid project. Be your own first reviewer.

            
Classwork: faculty browses your live URL and scores it with a rubric on layout, a11y and git hygiene.

            
Homework: fix the blocking issues.

            
The real marks and wording come from your faculty’s rubric. The checklist below is practice material built around those three areas, so nothing surprises you.

        

        

            
Live URL
The address on the internet where your site lives, like https://your-username.github.io/your-repo/. A file on your own computer does not count.

            
Layout
Does the Grid layout work, and does it still work on a phone?

            
a11y
Short for accessibility (11 letters between the a and the y). Can everyone use the site, including people who use only a keyboard or a screen reader?

            
Git hygiene
A clean repository and clear commit messages.

            
Blocking issue
A problem that stops someone from using or reviewing your site, like a dead link, missing styles or a page that breaks on a phone.

        

    


    

        
Put your project on GitHub Pages

        
    
            
  1. Push your project to a repository on GitHub. The main page must be called index.html.
    2. 
            
  2. Open the repository, then go to Settings and then Pages.
    3. 
            
  3. Under “Build and deployment”, set the source to Deploy from a branch. Choose your main branch and the / (root) folder, then press Save.
    4. 
            
  4. Wait a minute or two, then open https://your-username.github.io/your-repo/.
    5. 
            
  5. Open that link in a private window to see what faculty sees. Menu names on GitHub may look slightly different.
    6. 
        

        
GitHub Pages is case-sensitive. Style.css and style.css are different files, and a mismatch is a classic reason for a site with no styles.

    


    

        
If your live URL is broken: symptoms and fixes

        

            

                
What you seeLikely causeHow to fix it

                
                    
“404: There isn’t a GitHub Pages site here”Pages is not switched on, the branch or folder is wrong, or it is still deploying.Check Settings, then Pages. Wait a couple of minutes. You can watch the deployment on the repository’s Actions tab.

                    
The README text shows instead of your siteThere is no index.html in the root folder.Rename your main file to index.html (all lowercase) and put it in the root.

                    
The page appears with no stylesThe CSS path is wrong, or the capital letters do not match.Open DevTools and look for a red 404 on the .css file. Make the path and the case match exactly.

                    
Images are missingWrong path, different capital letters, or spaces in the file name.Rename My Photo.JPG to my-photo.jpg and update the HTML.

                    
It works on my laptop but not onlineThe path starts with / or C:\, or the case differs (Windows ignores case, GitHub does not).Use relative paths like css/base.css. A path that starts with / points at the root of the whole site, not your repository folder.

                    
You still see the old versionThe new version has not finished deploying, or your browser kept a saved copy.Wait, then hard refresh with Ctrl + Shift + R, or open a private window.

                    
Other pages give a 404The link points to the wrong file name or path.Link to about.html exactly as the file is named, for example <a href="about.html">.

                
            

        

    


    

        
Layout: how to test your Grid project

        
    
            
  1. Open your live page and press F12 to open DevTools. Turn on the device toolbar (Ctrl + Shift + M on Windows, Cmd + Shift + M on Mac, in Chrome and Edge).
    2. 
            
  2. Test at three widths: 360px (phone), 768px (tablet) and 1280px (laptop).
    3. 
            
  3. At each width check four things: no sideways scrollbar, nothing overlapping, text readable without zooming, and images inside their boxes.
    4. 
            
  4. In the Elements panel, find the grid badge next to your grid container and click it. DevTools draws the grid lines over the page, so you can see the tracks and gaps.
    5. 
        

        

            

                
What you seeUsual causeFix

                
                    
A sideways scrollbar on a phoneSomething is wider than the screen: a fixed width: 500px, a big image, or a long word.Use max-width: 100%, and use fr or minmax() instead of fixed pixels.

                    
Squashed grid columns on a phoneToo many fixed columns for a narrow screen.Use repeat(auto-fit, minmax(240px, 1fr)), or a media query that switches to one column.

                    
Long content pushes a grid item out of its cellGrid items have min-width: auto by default, so they will not shrink below their content.Add min-width: 0 to the grid item.

                    
Images stretch or spill outNo sizing rule for images.img { max-width: 100%; height: auto; }

                    
Fine on a laptop, tiny and zoomed out on a phoneThe viewport meta tag is missing.Add <meta name="viewport" content="width=device-width, initial-scale=1"> to the <head>.

                
            

        

        

            
A grid that adapts by itself


.card-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));
  gap: 16px;
}
img {
  max-width: 100%;
  height: auto;
}

            
A page layout that stacks on phones


.page {
  display: grid;
  grid-template-columns: 220px 1fr;
  grid-template-areas:
    "head head"
    "side main"
    "foot foot";
  gap: 16px;
}
@media (max-width: 700px) {
  .page {
    grid-template-columns: 1fr;
    grid-template-areas:
      "head"
      "main"
      "side"
      "foot";
  }
}

        

    


    

        
Accessibility (a11y): what to check and how

        
Accessibility means everyone can use your site, including people who use only a keyboard, a screen reader or a very small screen. Here is each check with a way to test it.

        

            

                
CheckHow to test itWhat good looks like

                
                    
Language and titleView the page source.<html lang="en"> and a short <title>Meet the Team</title>.

                    
LandmarksLook for header, nav, main and footer in your HTML.Real tags instead of anonymous divs. Use only one main per page.

                    
HeadingsRead the headings as an outline.One h1, then h2, then h3, with no jumps. Choose a heading by its structure, and use CSS for its size.

                    
ImagesCheck every img for an alt attribute.A real picture: alt="Five students at a table". Decoration only: alt="". Do not start with “image of”.

                    
Colour contrastIn DevTools, click a colour swatch in the Styles panel. It shows the contrast ratio.At least 4.5 to 1 for normal text. At least 3 to 1 for large text (about 24px, or 18.66px bold).

                    
KeyboardPut the mouse aside and press Tab through the page.Every link and button can be reached, in a sensible order, and you can always see where focus is.

                    
Link textRead each link’s words on their own.“Read the Grid guide”, not “click here”.

                    
Form fields (if you have any)Click a label. The field should get focus.<label for="email">Email</label> and <input id="email" type="email">.

                
            

        

        

            
Keep a visible focus outline


/* Never write "outline: none" without a replacement. */
a:focus-visible,
button:focus-visible {
  outline: 3px solid #1d4ed8;
  outline-offset: 3px;
}

            
Run an automatic check


DevTools, then Lighthouse tab,
tick "Accessibility",
press "Analyze page load",
then fix every issue it lists.

        

        
Automatic tools only find some problems. Always do the keyboard test by hand, and read your headings and link text as a person would.

    


    

        
Git hygiene: what a clean repository looks like

        
Git hygiene is a habit: small commits, clear messages and no junk. This is the daily loop:


git status                          see what changed
git add .                           stage all changes (or name one file)
git commit -m "fix: stack grid on phones"
git push                            send your commits to GitHub
git log --oneline                   list your recent commits

        
    
            
  • Commit small. One idea per commit. The CSS split is one commit, and each bug fix is its own commit.
    • 
            
  • Push at least at the end of every class, so a laptop problem never loses your work.
    • 
            
  • Never commit secrets such as passwords or API keys. If you did, change the secret. Deleting the file is not enough, because Git history keeps it.
    • 
            
  • Keep junk out with a .gitignore file, and compress large images.
    • 
            
  • Write a README. It is the front page of your repository on GitHub.
    •

Which issue first? A guide to blocking issues

        
After the review you will have a list of problems. Do not fix them in a random order. Sort them like this:

        

            

                
PriorityWhat it meansExamples

                
                    
Fix firstBlocking: it stops someone from seeing or using the site.The live URL gives a 404. CSS or images do not load. The page is unusable on a phone. The links to the main pages are broken.

                    
Fix nextThe site works, but a rubric area loses marks.Missing alt text, low contrast, no visible focus outline, unclear commit messages, no README.

                    
Polish laterSmall improvements.Spacing details, nicer names, extra comments.

                
            

        

        
This is general guidance. Your faculty’s feedback is the final word on what counts as blocking.
